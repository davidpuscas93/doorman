# Performance: measuring and fixing

Notes from making Doorman slow on purpose with 300,000 tickets, measuring it, and fixing it.
Every number here was measured on this codebase, not quoted from a blog post.

---

## 0. The test data

300,000 tickets across 50 events (3 ticket types each, 2,000 tickets per type), 2,000 users,
~21,000 transactions. Generated by `npm run seed`, which ends with `ANALYZE`.

**That `ANALYZE` matters.** After a bulk load, Postgres's planner statistics are stale — it still
believes the tables are nearly empty until autovacuum catches up. Plans chosen from stale statistics
are not the plans production would choose, so every measurement would be fiction.

## 1. The two shapes of "slow"

Almost every slow endpoint is one of these:

- **One query doing too much work** — usually a sequential scan because an index is missing.
- **Too many queries** — the N+1 problem: query count growing with the number of rows.

They're diagnosed differently. The first shows up in `EXPLAIN`; the second shows up in the query log.

---

## 2. Reading `EXPLAIN (ANALYZE, BUFFERS)`

Read it **bottom-up** — the innermost indented node runs first, results flow upward.

The baseline, counting available tickets for one event with no index:

```
Finalize Aggregate  (actual time=21.126..22.855 rows=1 loops=1)
  Buffers: shared hit=8215 read=3628
  ->  Gather  (actual time=21.042..22.849 rows=3 loops=1)
        Workers Planned: 2
        Workers Launched: 2
        ->  Partial Aggregate  (actual time=15.854..15.855 rows=1 loops=3)
              ->  Parallel Seq Scan on tickets  (actual time=9.264..15.724 rows=1877 loops=3)
                    Filter: ((event_id = '...') AND (status = 'available'))
                    Rows Removed by Filter: 98126
Execution Time: 22.909 ms
```

What each part is telling you:

| Line | Meaning |
|---|---|
| `Seq Scan` | Postgres read the whole table. No usable index. |
| `Rows Removed by Filter: 98126` × `loops=3` | ~300,000 rows examined and discarded. |
| `Buffers: hit=8215 read=3628` | ~11,800 8KB blocks, ~92MB pulled through. `hit` = from cache, `read` = not. |
| `Workers Launched: 2` | Parallelised because the scan was big — compensating for the missing index, not solving it. |
| `rows=1975` (est) vs `rows=1877` (actual) | Good estimate — the `ANALYZE` doing its job. A wild mismatch here means stale statistics. |

**Use `Buffers` as the headline metric, not time.** Time varies with cache state and machine load.
Buffers are the actual work done, and they're reproducible.

### The key observation

The same query against an event with 8 available tickets took **23.0ms**. Against one with 5,631,
it took **22.9ms**.

> A sequential scan costs what the **table** costs, not what the **answer** costs.

That's why this never shows up in development, and why it degrades with data growth rather than
with traffic.

## 3. Indexes: three measurements

Same query, three states:

| Index | Time | Buffers | Plan |
|---|---|---|---|
| none | 22.9 ms | 11,843 | `Parallel Seq Scan` |
| `(event_id)` | 2.60 ms | 125 | `Bitmap Heap Scan` |
| `(event_id, status)` | **1.15 ms** | **8** | `Index Only Scan`, `Heap Fetches: 0` |

**20× faster, 1,480× less data touched.**

### Why the composite wins

With `(event_id)` alone the plan reads:

```
Bitmap Heap Scan on tickets
  Filter: (status = 'available')
  Rows Removed by Filter: 369
  Heap Blocks: exact=117
```

The index found the event's 6,000 rows quickly, then Postgres had to fetch 117 blocks **from the
table** to check `status`, and discarded 369 of them.

With `(event_id, status)`:

```
Index Only Scan using tickets_event_id_status_idx
  Heap Fetches: 0
```

Both columns needed were in the index, so the table was never touched at all. That's the best
available outcome for a query like this.

### Rules worth keeping

- **The leading column must be selective.** An index on `status` alone (3 values over 300k rows)
  is near-useless — any lookup matches a third of the table, so Postgres will scan instead.
- **Low cardinality is fine in a *later* column.** `(event_id, status)` is ordered by event first;
  status just narrows within that slice.
- **A composite index also serves its prefix.** `(event_id, status)` covers queries filtering on
  `event_id` alone, so a separate `(event_id)` index is redundant — drop it.
- **Indexes are not free.** Every insert and update maintains every index on the table, and they
  cost disk. Two indexes where one suffices is a write-throughput tax for nothing.
- **An index created by hand in psql exists only on your machine.** It belongs in a migration.

## 4. N+1

The events listing needs, per event, the organizer's name and the count of available tickets. The
obvious implementation loads the events, then loops:

```typescript
const events = await this.eventsRepository.find();
for (const event of events) {
  const organizer = await this.usersRepository.findOne({ where: { id: event.userId } });
  const available = await this.ticketsRepository.count({
    where: { eventId: event.id, status: 'available' },
  });
  ...
}
```

**Measured: 103 queries for 51 events.** One for the events, then two per event. The log also shows
the same organizer fetched twice, because some organizers run two events.

51 events → 103 queries. 5,000 events → 10,001.

### The fix: make the query count constant

```typescript
async findAll(limit = 20, offset = 0) {
  const events = await this.eventsRepository
    .createQueryBuilder('event')
    .leftJoinAndSelect('event.organizer', 'organizer')   // organizer in the same query
    .orderBy('event.startsAt', 'ASC')
    .take(limit)
    .skip(offset)
    .getMany();

  if (events.length === 0) return [];

  const counts = await this.ticketsRepository            // one grouped count for all of them
    .createQueryBuilder('ticket')
    .select('ticket.eventId', 'eventId')
    .addSelect('COUNT(*)', 'available')
    .where('ticket.eventId IN (:...ids)', { ids: events.map((e) => e.id) })
    .andWhere('ticket.status = :status', { status: 'available' })
    .groupBy('ticket.eventId')
    .getRawMany<{ eventId: string; available: string }>();

  const availableByEvent = new Map(
    counts.map((c) => [c.eventId, Number(c.available)]),
  );

  return events.map((event) => ({
    id: event.id,
    title: event.title,
    startsAt: event.startsAt,
    organizer: event.organizer?.name ?? null,
    available: availableByEvent.get(event.id) ?? 0,
  }));
}
```

**Measured: 103 → 3 queries**, and it stays at 3 whatever the page size.

Notes:

- The fix is not always "one big join". Here it's *two targeted queries plus a `Map`* — joining
  300,000 ticket rows to aggregate them would often be worse than a grouped count restricted to the
  ids on this page. The principle is **constant query count**, not "one query".
- `COUNT(*)` comes back as a **string** — bigint doesn't fit safely in a JS number, so the driver
  won't guess. Hence `Number(c.available)`.
- Stitching in JS with a `Map` is cheap because it's page-sized (20 items), not table-sized.

## 5. Pagination

`take`/`skip` rather than `limit`/`offset`, because there's a join.

With a join, a naive `LIMIT 5` would cut **joined rows**, not entities — an event with three joined
rows would eat three of your five. So TypeORM runs two phases: a `SELECT DISTINCT ... LIMIT 5` to
pick five event ids, then the real query with `WHERE id IN (those five)`. Hence three queries
rather than two. Still constant.

(The opposite applies with row locking: `FOR UPDATE` can't be applied through that subquery, so
locking queries need `limit`/`offset`. See `docs/concurrency-and-locking.md`.)

**Note on `OFFSET` at scale:** `OFFSET 50000` still makes Postgres walk and discard 50,000 rows.
Fine for a few pages; for deep pagination or infinite scroll, keyset pagination
(`WHERE starts_at > :lastSeen ORDER BY starts_at LIMIT 20`) stays constant-cost. Not needed here,
worth knowing.

## 6. The checklist

When an endpoint is slow:

1. **Count the queries first.** `logging: true` in `database.module.ts`, hit the endpoint, count.
   If the count scales with rows, it's N+1 — fix that before anything else. Turn logging back off.
2. **If it's one query, `EXPLAIN (ANALYZE, BUFFERS)` it.** Look for `Seq Scan`, a large
   `Rows Removed by Filter`, and the `Buffers` count.
3. **Check the estimates match reality.** Wild mismatches mean stale statistics — `ANALYZE`.
4. **Add the narrowest index that serves the query**, leading with the selective column. Measure
   again. Keep the buffer counts.
5. **Only then consider caching.** A cache in front of an unindexed query hides the problem and
   pushes it into invalidation, which is harder.

The order matters: fix the query count, then the query, then reach for infrastructure.
